## 0. 一页速览

**这套系统在干什么**

每周日 20:00 自动规划下一周 7 天的选题；之后每天 07:30 自动把当天那篇写出来、排版、上传到公众号**草稿箱**，并发一封结果邮件。你只需要去后台点「群发」。

**两条铁律**

1. **内容与提示词的真源是本地仓库**（`/workspaces/other/weixin/wechat-flow`），不是 250。改内容 → 改本地 → `./deploy/deploy.sh`。
2. **一切自动化只由 systemd timer 触发**，没有常驻进程、没有 openclaw。

**日常只需要 5 条命令**（都在 250 上跑，见 [2.1](#21-在-250-上执行命令的标准姿势)）

```bash
ssh root@192.168.0.250
E='export PATH=/root/.nvm/versions/node/v24.14.1/bin:$PATH HOME=/root DISPLAY=:99'; cd /root/wechat-flow

eval $E; bun src/cli.ts accounts              # 谁在推、谁停了
eval $E; bun src/cli.ts status --all          # 本周计划 + 已推列表
eval $E; bun src/cli.ts drafts --all          # 草稿箱里到底有什么
eval $E; bun src/cli.ts doctor --all          # 体检
systemctl list-timers 'wechat-*' --all        # 下次自动跑是什么时候
```

**两个公众号**

| alias | 名称 | 配色 | CDP 端口 | 数据目录 | 状态 |
|---|---|---|---|---|---|
| `second` | 巧思初数 | blue | 9222 | `data/second` | ★ 默认账号 |
| `gaoh` | gaoh的技术分享 | green | 9223 | `data/gaoh` | 启用 |

**三种"改东西"的入口**

| 我想改… | 改哪里 | 生效时间 |
|---|---|---|
| 某个号推不推 | 250 的 `config.json` → `accounts.<alias>.enabled` | 下次 `--all` 运行立即生效 |
| 选题大纲 / 七天节奏 / 文章写法 | 本地 `content/` `prompts/` → 部署 | 下次生成文章时 |
| 本周已排好的 7 个选题 | 250 的 `data/<alias>/plans/<周>.json` | 立即（发布时才读计划） |

## 1. 系统是什么、怎么跑起来的

### 1.1 一张图

```

      └───────────────────┘                                    └──────────┬───────────┘

                                                          │  · 封面 ImageMagick 模板       │

                                                          │  · manim scene.py → scene.gif  │

                                                          └───────────────┬──────────────┘
                                                                          │
                                                       ✅ 邮件通知（含正文附件）/ ❌ 失败邮件
```

**设计原则（决定了后面所有细节）**

- **AI 只负责"内容"，其余全部确定性**。封面生成与上传、排版、校验、通知都是代码，可复现、可重跑。
- **不信上游的自报成功，只信后台真实 DOM**（`verifyDraftBody`）。这条来自一次真实事故（见 [9.1](#91-事故一草稿箱里只有标题没有正文)）。
- **主题与引擎解耦**。引擎不认"数学"，只认 `contentDir` / `promptsDir` / `model`。换学科 = 换这几个配置。

### 1.4 定时器：唯一的自动化入口

```bash
# 查看（这是判断"明天会不会自动发"的唯一方法）
systemctl list-timers 'wechat-*' --all

# 单元文件
/etc/systemd/system/wechat-plan.service      wechat-plan.timer
/etc/systemd/system/wechat-publish.service   wechat-publish.timer

# 手动触发一次（不等到点）
systemctl start wechat-publish.service
journalctl -u wechat-publish.service -n 100 -f     # 看它跑到哪了
```

| 定时器 | 时间 | 执行 | 说明 |
|---|---|---|---|
| `wechat-plan.timer` | **周日 20:00** | `cli.ts plan --all` | 编排下周 7 天 |
| `wechat-publish.timer` | **每天 07:30** | `cli.ts publish --all` | 只发"今天"那一篇 |
| `wechat-keepalive.timer` | **每 5 小时**（开机 10 分后首跑） | `cli.ts keepalive --all` | 顺延 4 天登录票据，掉线就等于所有发布失败 |

三个 timer 都是 `Persistent=true`：如果到点时机器关着，**开机后会立刻补跑一次**。
`wechat-publish.service` 里 `TimeoutStartSec=3000`（50 分钟），因为要等 pi、渲染、上传。

> ⚠️ `publish --all` 只作用于 `enabled: true` 的账号 —— 见 [第 4 章](#4-专题二控制某个账号是否推送enabled-开关)。

## 2. 命令速查

### 2.1 在 250 上执行命令的标准姿势

```bash
ssh root@192.168.0.250
export PATH=/root/.nvm/versions/node/v24.14.1/bin:$PATH HOME=/root DISPLAY=:99
cd /root/wechat-flow

bun src/cli.ts <命令> [参数]
```

一行版（脚本里用）：

```bash
ssh root@192.168.0.250 'export PATH=/root/.nvm/versions/node/v24.14.1/bin:$PATH HOME=/root DISPLAY=:99; cd /root/wechat-flow && bun src/cli.ts status --all'
```

**三个环境变量都必须有**：少了 `PATH` 找不到 `bun`；少了 `HOME` 读不到 pi 的模型配置和登录态；少了 `DISPLAY` 起不了 Chrome。

### 2.2 命令清单

| 命令 | 作用 | 常用参数 |
|---|---|---|
| `accounts` | 列出所有账号与启用状态（★ 默认 / 启用 / 停用） | — |
| `status` | 该号已发布的列表 + 现有计划文件 | `-a` `--all` |
| `plan` | 生成/重生成某周 7 天选题计划 | `--date YYYY-MM-DD`（以该日所在周为准）、`--dry-run`、`-a`、`--all` |
| `publish` | 生成并发布**某一天**的文章 | `--date`、`--dry-run`、`--reuse`、`--force`、`-a`、`--all` |
| `run` | 智能兜底：今天有计划就发布，没计划就先跑 `plan` | `--dry-run`、`-a`、`--all` |
| `doctor` | 体检（环境、登录态、技能、正文写入能力、公式、manim） | `-a` `--all` |
| `drafts` | 查草稿箱真实内容；带 `--date` 还会校验当天正文 | `--date`、`-a`、`--all` |
| `cover` | 给草稿自动上传封面（O-B）；`--probe` 只读探测封面弹窗 DOM | `--date`、`--title`、`--cover`、`--probe`、`-a` |
| `login` | 重新登录（扫码/给二维码发邮件） | `--qr`、`--wait 秒`、`-a` |
| `keepalive` | 会话保活（一次鉴权请求把 4 天票据顺延）；**成功后自动快照 + 到期预警** | `-a`、`--all`、`--wait 秒`、`--no-qr` |
| `session` | 会话三态判定 / cookie 快照 / 回滚（C1） | `probe`、`snapshot`、`restore --id`、`list`；`--json`、`--reload`、`--reason`、`--keep` |
| `mail-test` | 发一封测试邮件 | `-t a@b,c@d` |

**账号选择优先级**

```
-a/--account <alias>   ←  最优先（不受 enabled 限制，可以强推停用的号）
        ↓ 没写的话
环境变量 MW_ACCOUNT
        ↓ 没写的话
config.json 的 defaultAccount          （当前 = second）
```

`--all` = 所有 `enabled: true` 的号。

**`publish` 的三个行为开关（最容易搞混，务必分清）**

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只生成 + 打印，**不调技能、不写草稿箱、不发邮件** |
| `--reuse` | 文章 `.md` 已存在就直接用，**不重新调 pi 生成**（省模型额度、可反复调试） |
| `--force` | 无视 `state/published.json` 里"已发布"的记录，强制重发一次 |

典型组合：
```bash
# 调试排版：用已有文章重发一遍，不花钱
bun src/cli.ts publish -a gaoh --date 2026-10-13 --reuse --force
# 只出文章不动线上
bun src/cli.ts publish --all --date 2026-10-13 --dry-run
```

### 2.3 草稿封面自动上传（`cover`，O-B）

背景：skill 的**浏览器**发布流程只把正文写进草稿箱，**不会设置封面**（API 方式才带 `--cover`）。
封面由 ImageMagick 生成在 `imgs/<日期>/cover.png`，默认需在后台手动选。开启 `cover.uploadToDraft` 后，
发布流程会在**正文校验通过后**，用同一个已登录的 CDP 会话打开草稿编辑器，驱动封面弹窗上传 `cover.png`。

为什么不走 API：API 要 `access_token` + IP 白名单；浏览器会话走 cookie/token，不受白名单限制（同 D1）。

```bash
# 只读探测：dump 封面弹窗 DOM（不改任何内容），据此校准 code 里的 COVER_SELECTORS
eval $E; bun src/cli.ts cover --date 2026-10-13 --probe
eval $E; bun src/cli.ts cover --date 2026-10-13 --probe --explore   # 额外注入 coverPath 做一次完整彩排（有副作用，慎用）

# 给当天草稿补/换封面（回填、测试）；草稿已有封面时会覆盖
eval $E; bun src/cli.ts cover --date 2026-10-13
eval $E; bun src/cli.ts cover --date 2026-10-13 --title "标题" --cover /path/to/cover.png
```

开启开关（`config.json`，也可按账号覆盖）：
```json
"cover": { "mode": "template", "font": "", "uploadToDraft": true }
```

**AI 出图成本护栏（`cover.ai.dailyBudget`，C2/R6）**：`dailyBudget` 默认 `0` = 不限；设为 N 则每账号每天最多 N 次 AI 出图，超出自动降级 ffmpeg 并打 WARN（计数落 `data/<别名>/state/cover-budget.json`，按文章日期跨日归零，`cover --ai` 手动重画也计入）。

**真实流程（250 实测，O-B 两步弹窗）**：
1. 点 `#js_cover_area`（空态文案「拖拽或选择封面」）→ 打开操作浮层；
2. 点「从图片库选择」（`a.js_imagedialog`）→ 打开 **「选择图片」弹窗**；
3. 在该弹窗的 `input[type=file]` 上用 `DOM.setFileInputFiles` 注入 `cover.png`（文件框走 DOM 树遍历 + 祖先路径打分，**避开正文插图 `js_editor_insertimage` 的诱饵 input**）；
4. 等图片**自动选中**且「下一步」可点 → 点「下一步」；
5. 进 **「编辑封面」弹窗** → 点「确认」；
6. **轮询** `#js_cover_area` 预览的 `background-image` 变真实 URL → 点 `#js_submit button` 保存。

设计要点（为什么稳）：
- **失败绝不阻断发布**：任一步失败只写 warn + 邮件保留“请手动选封面”，正文照常发布（`publish` 仍 `done`）。
- **候选选择器 + 文本兜底**：入口/文件框/确认按钮都按一组候选依次尝试，再兜底可见元素文本。
- **只认真实结果**：上传前后对封面 DOM 取 `background-image`（或 `img.src`）对比，变了才算成功（对齐 `verifyDraftBody` 的“只信真实 DOM”）。
- **不做缩略图兜底**：上传失败时**不**点首个缩略图，避免误设图库里的旧图为封面；宁可 `ok:false` 降级。
- **可回滚**：`uploadToDraft:false` 即完全退回旧行为；改动集中在 `wechat.ts`（新增函数）/`publisher.ts`（一段 try/catch）/`cli.ts`（新命令）。

排障：看 `cover --probe` 输出里的 `entryMatch` / `fileInputs` / `coverVisuals` / `coverClassEls` / `iframes`。
若封面弹窗在 iframe 内或选择器不同，据此更新 `src/wechat.ts` 顶部的 `COVER_SELECTORS`（`fileInput` 走 DOM 树遍历，已能覆盖 iframe/shadow）。

常见坑（勿回退）：保存必须点 `#js_submit button`（点容器无效，封面不持久）；点「确认」后必须**轮询**背景图（异步 XHR，立即读会误判失败）；上传后必须等**自动选中**再点「下一步」。完整验收步骤见 [`deploy/ACCEPTANCE-250.md`](../deploy/ACCEPTANCE-250.md)。

### 2.4 会话寿命管理（C1：保活 / 快照 / 回滚）

公众号后台的浏览器凭证（`slave_sid` 等）是**硬 4 天（96h）到期**，微信只在“有鉴权请求”时顺延。
所以这里有三层保护：**保活（顺延）→ 快照（可回滚）→ 到期预警（提前 24h 通知）**。

**a) 保活节奏：每 5 小时一次（`wechat-keepalive.timer`）**

```bash
systemctl list-timers 'wechat-keepalive*' --all     # 看下次什么时候跑
systemctl start wechat-keepalive.service            # 手动跑一次
journalctl -u wechat-keepalive.service -n 50 --no-pager
```

为什么是 5h：票据 96h 才硬过期，5h 一次意味着**连续漏跑 19 次**才会真的掉线，同时一天只多花几分钟 CPU。
间隔可改（不用编辑 unit 文件）：

```bash
WFC_KEEPALIVE_HOURS=4 bash deploy/install.sh   # 渲染 wechat-keepalive.timer.d/interval.conf
bash deploy/install.sh                         # 不带变量 = 删掉 drop-in，回到 unit 里的 5h
```

精度 `AccuracySec=5m`：允许 systemd 把运行时间在 ±5 分钟内挪动（省唤醒），对 96h 的窗口无影响。

**b) 快照：每次保活成功后自动留一份“回滚点”**

```bash
bun src/cli.ts session list                      # 看有哪些快照（新→旧）
bun src/cli.ts session snapshot --reason manual    # 手动拍一份
bun src/cli.ts session restore --id 2026-10-20T03-53-15-317Z
```

- 内容：`Default/Cookies`（真 SQLite）+ `Local State`（解 cookie 的密钥）**成对**保存——只留一个等于没留；
- 位置：`data/<alias>/session-snapshots/<id>/`，目录 `0700` / 文件 `0600`；`data/` 已被 `.gitignore` 与 `deploy.sh` 排除，**不会进库、不会上 250、不会被备份脚本带走**；
- 幂等：同一天同一分钟内、同一 `reason` 只留一份（`keepalive` 跑两次不会写两份）；
- 保留：默认最近 **10** 份（`--keep N` 可调），`pruneSnapshots` 在每次 snapshot 后自动执行；
- 拒绝条件（显式 `ok:false`，绝不静默）：`Cookies` 或 `Local State` 不存在、复制后 `sha256`/`PRAGMA integrity_check` 对不上（会重试一次）。

**c) 回滚：`session restore --id <id>`**

顺序是硬要求，不要手工改：

1. 校验快照 `sha256` + 文件大小 → 再跑 `PRAGMA integrity_check`（**先验后动**，坏快照在这里就被挡住，现网一个字节都不动）；
2. `systemctl stop wechat-browser@<alias>.service`——浏览器还持有 SQLite 时替换文件 = 数据丢失，所以 **stop 失败就中止**（unit 不存在只 warn，因为 inline 模式没有 unit）；
3. 现网文件备份为 `*.pre-restore`；
4. 删 `-journal`/`-wal`/`-shm` 侧车文件 → 替换 → 再验 `integrity_check`；
5. 任何后续步骤失败 → **自动回滚到 `*.pre-restore`**（幂等：内容已一致就不重复写），并在 `reason` 里明说；
6. `systemctl start` → 打印 `needsReverify:true`，CLI 随后做一次**只读**复验并给出证据。

> ⚠️ **复验仍 `invalid` = 快照回滚无效**：说明 MP 服务端已经真的把这套凭证作废了（不是本地文件问题），只能重新扫码：
> `bun src/cli.ts login -a <alias> --qr --wait 900`。

**d) 到期预警邮件（提前 24h，最多一封/24h）**

`keepalive` 每次结束后读一次 cookie 到期时间：剩余 < 24h 就发一封**预警**邮件。
它与“失败邮件/二维码邮件”**用词完全分开**（标题带 ⏳ 和“提前预警，非失败”），避免把“还有 24 小时可以慢慢处理”误读成“已经挂了”。
状态记在 `data/<alias>/state/session-warn.json`；发送失败**不推进** `lastWarnAt`（下次保活会重试）。
**它永远不会阻断发布**：预警只是日志 + 邮件。

**e) 三态判定别搞混**

```bash
bun src/cli.ts session probe -a <alias>           # 只读，三层证据（cookie / HTTP / DOM）
bun src/cli.ts session probe -a <alias> --json     # 给控制台/脚本用
bun src/cli.ts session probe -a <alias> --reload   # 强制禁缓存重载再读 DOM（会扰动当前 tab）
```

`valid` / `invalid` / `unknown`：**cookie 库读不到必须落 `unknown`，不能落 `invalid`**——否则会无端触发扫码流程（2026-10-20 07:02 的血训）。

### 2.5 浏览器独立托管（C1 Step5：重启 console 不再碰登录态）

**谁拥有 Chrome**（这是「改代码要不要重新扫码」的结构性答案）：

```
wechat-xvfb.service          Xvfb :99（共享显示，两个 Chrome 都渲染在这里）
wechat-browser@second.service   Chrome（profile=wechat-second, CDP :9222）
wechat-browser@gaoh.service     Chrome（profile=wechat-gaoh,   CDP :9223）
wechat-console.service          只是 CDP 客户端：不再 spawn Chrome
```

- 重启/部署 `wechat-console` **不碰**浏览器 → 登录态不受影响（AC4）。
- 浏览器不再寄生在 SSH 登录会话的 cgroup 里（那是 2026-10-20 诊断出的 E4 隐患）。
- **每 alias 只有一个实例**：unit 名就是锁。同 profile 双开会被微信判成异常登录、直接踢线并要扫码。
- Chrome 参数**只**存在于 `src/browser.ts#buildChromeArgs`；`wechat-browser@.service` 通过
  `src/browser-agent.ts` 启动（agent 用 `execve` 把自身换成 Chrome，所以 systemd 的 MainPID 就是 Chrome）。
  **不要**把 `--user-data-dir` / 窗口尺寸等参数抄进 unit 文件 —— 指纹一变就会触发风控。

**a) 托管方式怎么决定**

| 场景 | 行为 |
|---|---|
| `WFC_BROWSER_MODE=external` | unit 托管（`ensureBrowser` 只 `systemctl start`，**绝不** spawn） |
| `WFC_BROWSER_MODE=inline` | 回滚态：console 自己 spawn Chrome（旧行为） |
| 未设置（默认） | 自动：本机有 `wechat-browser@<alias>.service` → external，否则 inline |

`bun src/cli.ts doctor --all` 里 `browser 托管方式` 一行会打印当前判定与来源。

**b) 迁移（只做一次；在当天发布完成后的窗口，全程不需要扫码）**

```bash
# ① 先装 unit（安装器只 enable xvfb、不 enable 具体 alias 实例）
#    250 是控制台模式 → 用 install-console.sh；纯 timer 模式才用 install.sh
bash deploy/systemd/install-browser-units.sh    # 只装 unit；也可直接跑下面任一安装器
bash deploy/install-console.sh                  # 控制台模式（250）

# ② 停掉旧的裸进程（顺序不能反：先 Chrome 让它 flush Cookies，再 Xvfb）
systemctl stop wechat-console.service
pgrep -x chrome | xargs -r kill -TERM    # 裸 Chrome 优雅退出（SIGTERM → flush Cookies）
# ⚠️ 别用 `pkill -f '--remote-debugging-port'`：这条 ssh 命令行本身也含该字符串，
#    pkill 会把你自己这条会话一起杀掉。`-x` 按进程名精确匹配，安全。
sleep 5 && pgrep -x chrome && echo "⚠️ chrome 还没退完，等一下再继续" || true
pgrep -x Xvfb | xargs -r kill -TERM      # 裸 Xvfb（会带走还没退出的 Chrome）
sleep 3 && pgrep -x Xvfb || true

# ③ 交给 systemd
systemctl start wechat-xvfb.service
systemctl enable --now wechat-browser@second.service wechat-browser@gaoh.service
systemctl restart wechat-console.service

# ④ 复验：两账号必须 valid、0 次扫码
cd /root/wechat-flow && bash deploy/session-check.sh
```

`session-check.sh` 除了看 unit 是否 `active`，还会核对 **MainPID 是不是 chrome**：
如果 unit 显示 active 但主进程不是 chrome，说明裸 Chrome 还占着 CDP 端口（迁移顺序错了），
agent 会拒起第二个实例并在 journal 里写明。

> **装完 unit 不会打断当天发布**：模板一存在，托管方式就自动判成 `external`；但若裸 Chrome
> 还占着 CDP 端口（9222/9223），`ensureBrowser` 会在 `cdpVersion` 处短路直接复用，**不会**
> 起第二个 Chrome。真正接管发生在上面第 ②～③ 步（停掉裸进程）之后。

**c) 回退到 inline（一键）**

```bash
systemctl set-environment WFC_BROWSER_MODE=inline   # 或写进 /etc/default/wechat-console / .env
systemctl restart wechat-console.service
systemctl disable --now wechat-browser@second.service wechat-browser@gaoh.service
# 确认：bun src/cli.ts doctor --all 的 browser 托管方式 = inline
```

> inline 模式有前置守卫：若对应 `wechat-browser@<alias>.service` 仍 active，会**拒绝** spawn 并报错
> （防双实例）。所以回退顺序是「先 disable --now，再 restart console」。

**d) 排障三件套**

```bash
systemctl status wechat-browser@second.service --no-pager
journalctl -u wechat-browser@second.service -n 80 --no-pager   # Chrome 自己的日志（SyslogIdentifier=wechat-browser-second）
systemctl show wechat-browser@second.service -p MainPID --value # 必须是一个 chrome 进程
cd /root/wechat-flow && bash deploy/session-check.sh            # 一键自检（含会话三态）
```

常见故障：

| 现象 | 原因 / 处置 |
|---|---|
| unit 起不来，日志 `Failed to connect to the bus` / `cannot open display` | Xvfb 没起：`systemctl start wechat-xvfb.service`（本 unit `Requires=` 它） |
| `Xvfb` 启动失败 `server already active for display 99` | 本机还有裸 `Xvfb :99`：先 `pkill -TERM -f 'Xvfb :99'`，再 start unit |
| agent 日志「CDP :9222 已在监听…拒绝启动第二个实例」 | 有别的 Chrome 占着端口（迁移前的裸 Chrome，或 inline 起的）。停掉它再 `systemctl restart wechat-browser@second` |
| `systemctl --failed` 里有 wechat-browser@… | 5 分钟内连挂 10 次会停止重试（`StartLimitBurst=10`）：按上面日志修根因，再 `systemctl reset-failed wechat-browser@second` + start |
| 停浏览器后 cookie DB 坏了 | 本 unit 用 `KillMode=mixed` + `TimeoutStopSec=20`（先 SIGTERM 让 Chrome flush）。**不要**改成 `systemctl kill -s SIGKILL` / `KillMode=control-group` |

### 3.2 内容主题由 4 个文件决定

```
content/syllabus.md      ← "能选哪些知识"（知识大纲，越全越好）
prompts/plan.md          ← "一周 7 天怎么分配"（节奏 + 生成计划的指令）
prompts/editor.md        ← "编辑是谁"（人设，plan 和 article 都会加载）
prompts/article.md       ← "一篇文章长什么样"（字数/结构/公式/动图规则）
```

**四者关系**：`plan.md` 让 agent 读 `syllabus.md`（再读已发布清单去重）产出 `plans/<周>.json`；
`article.md` 让 agent 读 `plans/<周>.json` 里当天那条，产出 `articles/<日期>.md`。

```jsonc
  "enabled": true,
  "dataDir": "./data/eng"
}
```

> 发布时给技能传的是 `contentDir`/`promptsDir` 里的文件，与 `dataDir` 分开，因此**多学科互不干扰**。
> 如果某学科的公式/动图不该出现，在该账号上加 `"math": {"enabled": false}`、`"manim": {"enabled": false}`。

## 4. 【专题二】控制某个账号是否推送（enabled 开关）

### 4.1 开关在哪

`/root/wechat-flow/config.json` → `accounts.<alias>.enabled`

```bash
# 用命令改（比手改 json 安全）
ssh root@192.168.0.250
cd /root/wechat-flow
python3 - <<'PY'
import json
p="config.json"; c=json.load(open(p))
c["accounts"]["gaoh"]["enabled"] = False     # False 停推 / True 恢复
json.dump(c, open(p,"w"), ensure_ascii=False, indent=2)
PY
bun src/cli.ts accounts                      # 立刻看到 "停用"
```

改完**不需要重启任何东西**——`publish`/`plan` 每次运行都重新读 `config.json`。

### 4.2 精确语义（已实测，别猜）

| 写法 | `enabled: true` | `enabled: false` |
|---|---|---|
| `publish --all` | ✅ 会推 | ❌ **跳过** |
| `plan --all` | ✅ 会编排 | ❌ 跳过 |
| `publish -a gaoh` | ✅ 会推 | ✅ **仍会推**（`-a` 显式指定绕过开关） |
| 不写 `-a`（用默认账号） | ✅ 会推 | ✅ 仍会推（默认账号除非显式写 `false`，否则视为启用） |

实测证据（2026-10-12）：

```
=== gaoh 启用时 ===
$ bun src/cli.ts publish --all --date 2026-10-12
────── second ──────
[INFO] already published 2026-10-12; skip
────── gaoh ──────                       ← 出现了
[INFO] already published 2026-10-12; skip

=== gaoh 改成 enabled:false 后 ===
$ bun src/cli.ts publish --all --date 2026-10-12
[INFO] already published 2026-10-12; skip    ← 只剩 second，gaoh 的横幅都没了

$ bun src/cli.ts status -a gaoh              ← 显式指定仍然可用
published : 1 total
  2026-10-12  ✅  十字相乘法不难，难的是没人告诉你「凑数」有固定套路
```

**结论**：`enabled` 是"**自动流程的参与开关**"，不是"封号锁"。定时器跑的是 `--all`，所以
**停用 = 定时器不会再碰它**，这是你想要的日常语义；而临时手动补发仍然可以。

> 默认账号（`second`）比较特殊：`enabled` 省略时视为 `true`；其他账号省略时视为 `false`。
> 所以新增账号**必须显式写 `"enabled": true`** 才会进入自动流程。

### 4.3 三种停推场景

**场景 1：临时停几天（比如内容审核期）**

```bash
# 关掉
python3 -c "import json;p='config.json';c=json.load(open(p));c['accounts']['second']['enabled']=False;json.dump(c,open(p,'w'),ensure_ascii=False,indent=2)"
bun src/cli.ts accounts      # 确认显示「停用」
```
定时器照常运行，但不会碰这个号。**不会漏推也无需改定时器——恢复后从当天开始继续。**

**场景 2：彻底不用了** → 直接删掉 `accounts` 里那段。

**场景 3：只想暂停一周不停用**
关掉 `enabled` 一周再打开；或者更精细地在计划文件里把不想发的日期去掉
（`findEntryForDate` 找不到当天条目 → `publish` 报 `no plan for <date>` 并跳过）。

**忘记自己关过？**

```bash
bun src/cli.ts accounts        # ★ 默认 /   启用 /   停用
```

### 4.4 顺带：邮件通知的开关

```jsonc
"notify": {
  "enabled": false,            // 总开关（telegram 用）；email 有自己的 enabled
```

## 5. 【专题三】这一周推完后，怎样开启下一周

### 5.1 结论：正常情况下你什么都不用做

```bash
systemctl list-timers 'wechat-*' --all
# NEXT                        UNIT
# Sun 2026-10-18 20:00:00 CST wechat-plan.timer     ← 会自动排下周
# Tue 2026-10-13 07:30:00 CST wechat-publish.timer  ← 每天 07:30 一篇
```

周日 20:00 → 生成 `plans/2026-W43.json`（下周 7 天）；
周一 07:30 → `publish` 用 `findEntryForDate` 找到下周一那条 → 发出去。**无人工介入。**

**为什么下周也找得到计划**：`findEntryForDate()` 会扫描 `plans/` 目录下**所有** JSON，
按 `date` 字段匹配"今天"，不关心是哪个周文件。所以下周文件一生成，下周一就能用。

### 5.2 周与周的衔接（时间线）

| 时间 | 发生什么 | 产物 |
|---|---|---|
| 周日 20:00 | `plan` 编排下周 | `data/<alias>/plans/2026-W43.json`（7 条） |
| 周一 07:30 | `publish` 发周一 | 草稿箱 + 邮件 + `state/published.json` 落一条 |
| … 每天 07:30 | 直到周日 07:30 发完 | 本周 7 篇齐 |
| 周日 20:00 | 又到编排时刻 → 生成 `2026-W44.json` | 循环 |

**每周一自查（1 分钟）**

```bash
E='export PATH=/root/.nvm/versions/node/v24.14.1/bin:$PATH HOME=/root DISPLAY=:99'; cd /root/wechat-flow
eval $E; bun src/cli.ts status --all | grep -E "plans|published"
eval $E; bun src/cli.ts drafts --all      # 上周 7 篇是否都进了草稿箱
systemctl list-timers 'wechat-*' --all    # 下周的 plan timer 还在
```

### 5.3 如果周日那次没跑成（失败/机器关机）

**关机** → `Persistent=true`，开机后自动补跑。

**跑失败了**（模型超时等）→ 手动补：

```bash
ssh root@192.168.0.250
export PATH=/root/.nvm/versions/node/v24.14.1/bin:$PATH HOME=/root DISPLAY=:99; cd /root/wechat-flow
bun src/cli.ts plan --all                 # 补编排（会覆盖同周文件）
journalctl -u wechat-plan.service -n 120  # 看上次为什么失败
```

**只想补某一个号**：`bun src/cli.ts plan -a gaoh`

**只想知道会不会成功、先不动线上**：
```bash
bun src/cli.ts plan -a second --dry-run   # 产出校验通过后自动丢弃，不覆盖本周计划
```

### 5.4 想让"下周"换成别的内容安排

| 目标 | 做法 |
|---|---|
| 换下周 7 个选题 | 按 [3.7](#37-实操手工指定本周-7-个选题) 改 `plans/2026-W43.json` |
| 换长期的节奏（模块分配） | 改 `prompts/plan.md`（本地改 → 部署） |
| 换大纲（可选知识范围） | 改 `content/syllabus.md` → 部署 |
| 下周整体停推 | 该号 `enabled: false`（[第 4 章](#4-专题二控制某个账号是否推送enabled-开关)） |
| 下周只推某几天 | 在周计划里删掉不想推的 `days` 条目 |

### 5.5 补推已过去的那一天

```bash
# 今天该发但没发（例如早上机器没开）→ 现在补，走同一条链路
bun src/cli.ts publish --all --date 2026-10-13

# 已经发过、想重发（会新增一个草稿，旧的不删）
bun src/cli.ts publish -a second --date 2026-10-13 --force --reuse
```

## 6. 【专题四】manim + ffmpeg 生成 GIF 并嵌入文章

### 6.1 为什么必须是 GIF，不能是 MP4

公众号正文**只能内联图片**。实测：GIF 会以 `https://mmbiz.qpic.cn/mmbiz_gif/...` 上传并正常播放
（微信会把宽度重设为 `data-w=640`）；MP4 无法自动插入正文。所以 `wechat-flow` 只做 GIF。

### 6.2 内容规格（实测数值）

| 项 | 建议 | 实测体积 |
|---|---|---|
| 宽度 | 720px（微信会重设为 640） | — |
| 帧率 | 12 fps（10~15 均可） | — |
| 时长 | 3~8 秒 | — |
| **体积** | **≤ 1~2 MB**（越小越好） | 720px/12fps = **52 KB**；600px/10fps = **36 KB**；800px/15fps = **76 KB** |
| 数量 | 一篇文章最多 1 张 | — |

体积实测远低于上限，**放心用**。`bin/manim-gif.sh` 会在超过 `--max-mb` 时自动降档重压。

### 6.3 用法一（推荐，全自动）：让 agent 写 scene.py，管线自动渲染

**你什么都不用做。**发布流程会检查 `data/<alias>/imgs/<日期>/scene.py`：

```
存在 scene.py 且 scene.gif 不存在（或比 scene.py 旧）
        ↓
自动执行 bin/manim-gif.sh scene.py Scene -o scene.gif --width 720 --fps 12
        ↓
文章里 ![](../imgs/<日期>/scene.gif) 指向的文件就存在了
```

**约束（必须遵守，否则渲染失败）**：

1. 场景文件路径固定：`data/<alias>/imgs/<日期>/scene.py`
2. **类名必须叫 `Scene`**（渲染命令按这个名字找类）
3. 只依赖 manim 自带对象；**不读外部文件、不联网**
4. 时长 3~8 秒；配色高对比（BLUE/YELLOW/RED/GREEN）；字号偏大（手机上看）

`prompts/article.md` 里已经把这些规则写给 agent 了，你也可以在 `prompts/editor.md` 里加全局约束
（例如"只有函数图象、图形变换、面积切割、动点问题才允许用动图"）。

一个可用的最小场景（实测通过）：

```python
from manim import *


class Scene(Scene):          # ← 类名必须是 Scene
    def construct(self):
        ax = Axes(x_range=[-2, 4, 1], y_range=[-1, 6, 1], x_length=5.0, y_length=2.8,
                  axis_config={"color": GREY_B}, tips=False)
        curve = ax.plot(lambda x: x**2 - 2*x + 1, color=BLUE, stroke_width=4)
        vline = ax.get_vertical_line(ax.c2p(1, 5), color=YELLOW)
        lbl = MathTex(r"y=x^2-2x+1", font_size=30, color=BLUE).to_corner(UR)
        self.play(Create(ax), run_time=1.0)
        self.play(Create(curve), FadeIn(lbl), run_time=1.5)
        self.play(Create(vline), run_time=0.8)
        self.wait(0.4)
```

文章里这样引用：

```markdown
下面这张动图展示的是抛物线 y=x²-2x+1 的对称轴位置：

![抛物线对称轴](../imgs/2026-10-14/scene.gif)
```

**试跑验证**（只验证渲染，不发布）：

```bash
ssh root@192.168.0.250
export PATH=/root/.nvm/versions/node/v24.14.1/bin:$PATH HOME=/root DISPLAY=:99; cd /root/wechat-flow
bash bin/manim-gif.sh data/gaoh/imgs/2026-10-14/scene.py Scene -o /tmp/t.gif --width 720 --fps 12
# ✅ /tmp/t.gif
#    52K  时长 2.666667s  宽高 720x405  原始mp4 28K
```

### 6.4 用法二：手动渲染任意场景

```bash
bash bin/manim-gif.sh <场景.py> <类名> [-o out.gif] [--width 720] [--fps 12] \
     [--quality ql|qm|qh] [--colors 128] [--max-mb 2] [--manim /opt/manim-venv/bin/manim] [--keep]
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--width` | 720 | GIF 宽度；自动降档时优先降它 |
| `--fps` | 12 | 帧率 |
| `--quality` | `ql` | manim 渲染画质（`ql`=480p15 最快，`qh`=1080p60 最清晰） |
| `--colors` | 128 | 调色板颜色数 |
| `--max-mb` | 2 | 超过就自动降宽/降帧/减色重压 |
| `--keep` | — | 保留中间 mp4（默认删除） |

渲染失败时会打印 manim 的最后 25 行输出，方便定位。

### 6.5 用法三：已有 GIF，直接放进文章

```bash
# 把做好的 gif 放到当天媒体目录
cp my.gif /root/wechat-flow/data/<alias>/imgs/2026-10-14/
# 文章里引用（路径相对 articles/ 目录；用绝对路径也可以）
# ![](../imgs/2026-10-14/my.gif)
```

支持 `.gif/.png/.jpg/.jpeg/.webp`。

### 6.6 关闭动图

```jsonc
"manim": { "enabled": false }        // 账号级：放在 accounts.<alias> 里
```

关闭后 `scene.py` 不会被渲染，`prompts/article.md` 里的 `{{manimEnabled}}` 变成 `false`，
agent 也被告知不要写场景。

### 6.7 排障

| 症状 | 原因 | 处理 |
|---|---|---|
| `manim 渲染失败` | 类名不是 `Scene` / 语法错误 | 看日志里 manim 的输出；`python3 -c "import ast;ast.parse(open('scene.py').read())"` 先查语法 |
| `找不到 manim：/opt/manim-venv/bin/manim` | 虚拟环境没了 | `ls /opt/manim-venv/bin/manim`；或 `--manim <路径>` |
| GIF 没被上传 | 文章里没引用 / 路径写错 | 检查 `![](../imgs/<日期>/xxx.gif)`；确认文件存在 |
| 动图在草稿里不动 | 上传的是 png 不是 gif | 用 `bun tools/draft-probe.ts 9223 open` 看 img 的 src 是不是 `mmbiz_gif` |
| 改了 scene.py 但没更新 | 缓存判断是"gif 比 scene.py 新就不重渲染" | 删掉 `scene.gif` 再发，或 `touch scene.py` |

## 7. 【专题五】用 LaTeX 编排公式

### 7.1 先讲清楚"为什么不能直接写 `$x^2$`"

上游排版库 `baoyu-md` 的数学扩展是这样注册的：

```js
const isBrowser = typeof window !== "undefined";   // renderer.ts
if (isBrowser) md.use(MDKatex, { nonStandard: true });
```

而发布技能是跑在 **bun/Node** 里的，`window` 永远是 `undefined` → **公式扩展从不启用**。
实测（草稿 100000114）：直接写 `$x=\frac{-b\pm\sqrt{b^2-4ac}}{2a}$` 会**字面**出现在正文里，
`svg` 数量 = 0；写 `\(a^2+b^2=c^2\)` 反斜杠还会被吃掉变成 `(a^2+b^2=c^2)`。

> 所以：**在 bun/Node 链路上，`$…$` 不会自己变成漂亮公式。**

### 7.2 现在怎么办：照常写 `$…$`，管线自动转成矢量 SVG

`wechat-flow` 在发布前加了一步确定性转换（`src/math.ts` + `bin/tex2svg.py`）：

```
articles/xxx.md                 ← 你/agent 写 $…$ 和 $$…$$
      ↓  pdflatex → dvisvgm --no-fonts --exact-bbox
articles/xxx.math.md            ← 公式变成内联 <svg>…</svg>（原文件不动）
      ↓  技能走浏览器 CDP 粘贴
公众号正文里的 <svg>           ← ✅ 实测存活
```

**你要做的只有一件事**：在文章里写 LaTeX。剩下的自动完成。

```markdown
先说求根公式 $x=\frac{-b\pm\sqrt{b^2-4ac}}{2a}$，它要求判别式非负。

一般式长这样：

$$y=ax^2+bx+c,\quad a\neq 0$$
```

### 7.3 为什么用内联 SVG 而不是 KaTeX/MathJax

| 方案 | 微信里能用吗 | 原因 |
|---|---|---|
| 内联 `<svg>` | ✅ **实测可用** | 微信保留 `<svg>` 标签；字形已转成路径，读者端**不需要数学字体** |
| KaTeX / MathJax | ❌ | 需要执行 JS、需要 `.katex` 类与一堆外部 CSS，微信全剥掉 |
| 公式图片（PNG） | ⚠️ 能用但丑 | 位图放大糊；SVG 是真矢量 |

**"存活"的证据**（草稿 100000116，走完整剪贴板粘贴链路）：

```
svg: 3   ← 3 个公式全部保留，viewBox 全对
样式保留: style="width:6.76em;height:1.5em"
实际盒子: 108×24 / 124×24 / 72×24 px
父节点:   行内公式在 <P> 里，块级公式在 <SECTION> 里   ← 位置也对
placeholderLeak: false      ← 没有把"从这里开始写正文"带进去
```

并且**保存草稿 → 关闭 → 重新打开后 SVG 依然在**。

### 7.4 单独使用转换工具 `bin/tex2svg.py`

```bash
python3 bin/tex2svg.py '<LaTeX>' [--display] [--height 1.5em] [--scale 1] [--color '#333333']
```

| 参数 | 意思 |
|---|---|
| `--display` | 块级公式（独立成行、居中、大一点）；不加就是行内 |
| `--height` | 渲染高度，默认 `1.5em`（约 24px） |
| `--scale` | 整体缩放系数，默认 1 |
| `--color` | 公式颜色，默认跟随正文 |

实测：

```bash
$ python3 bin/tex2svg.py 'x=\frac{-b\pm\sqrt{b^2-4ac}}{2a}'
<svg ... viewBox="0 0 71.334 15.829" style="width:6.76em;height:1.5em">...</svg>
$ python3 bin/tex2svg.py 'y=ax^2+bx+c,\quad a\neq 0' --display
<svg ... viewBox="0 0 112.503 12.537" style="width:13.461em;height:1.5em">...</svg>
```

> 底层是 `pdflatex -no-shell-escape` + `dvisvgm --pdf --no-fonts --exact-bbox`。
> `--no-fonts` 是关键：把字形转成**路径**，这样读者端不需要装任何数学字体。

### 7.5 支持的写法与语法限制

自动识别这四种写法（**代码块和行内反引号里的 `$` 会被跳过**，不会误伤）：

| 写法 | 类型 |
|---|---|
| `$...$` | 行内 |
| `$$...$$` | 块级 |
| `\(...\)` | 行内 |
| `\[...\]` | 块级 |

**硬限制（踩过的坑）**

1. ⚠️ **公式里不能有中文**。`\text{扇形}` 会直接报 Unicode 错误。
   → 中文写在公式外面：`扇形面积 $S=\frac{1}{2}lr$`，而不是 `$\text{扇形面积}=\frac{1}{2}lr$`
2. `\[ ... \]` 不能直接放进 `standalone` 文档类（报 `Missing $ inserted`），
   工具内部已自动改成 `$\displaystyle ...$`。
3. 环境里是 **`lualatex`**（无 `xelatex`）。需要中文时不要试图在公式里塞 CJK。

**"适当使用"的判据**（工具内置的保守规则，避免把 `$5`、`$100` 当成公式）：

- 内容必须含 LaTeX 命令或数学记号（`\frac`、`^`、`_`、`=`、`≠`、`√`、`∑`…）
- 内容不能是纯中文
- `$` 前后不能紧贴字母/数字（`$5` 不会被当公式）

**认不出来就原样保留**——宁可显示得难看，也不报错、不丢内容。

### 7.6 开关与调参

```jsonc
// config.json 顶层（两个号共用），或放进 accounts.<alias> 覆盖
"math": {
  "enabled": true,        // false = 完全关闭公式转换（$…$ 原样发出）
  "height": "1.5em",      // 行内公式高度
  "scale": 1,             // 整体缩放
  "color": "",            // 留空 = 跟正文颜色
  "python": "python3"
}
```

**只调大小**：把 `scale` 改成 `0.95`（略小）或 `1.1`（略大），比一个个改 `--height` 方便。
**换颜色**（例如要配 blue 主题）：`"color": "#2b6cb0"`。

### 7.7 缓存与排障

公式按 `sha1(tex + 行内/块级 + height + scale + color)` 缓存在
`data/<alias>/imgs/formula/<hash>.html`。**重复发布不重新编译**（第一次约 0.3~1 秒/条）。

```bash
# 缓存全清（改了 pdflatex/字体后需要）
rm -rf /root/wechat-flow/data/<alias>/imgs/formula
```

| 症状 | 原因 / 处理 |
|---|---|
| 正文里出现字面的 `$x^2$` | ①`math.enabled` 是 `false`；②`$…$` 内容没被识别成公式（太简单，如 `$5$`）→ 这是故意的保守行为 |
| 日志 `公式未渲染（已保留原文）` | LaTeX 语法错（常见：公式里有中文、括号不配对）。**不会阻断发布**，只是这条公式变纯文本 |
| `latex 公式 (pdflatex+dvisvgm) ❌` | `bun src/cli.ts doctor` 会指出来；装 `texlive` + `dvisvgm` |
| 公式在草稿里是空的 | 用 `bun tools/draft-probe.ts 9223 open` 看 `svg` 数量和 `viewBox` |

### 7.8 验收公式是否真的存活


`dollar: false`（说明正文里没有残留的 `$…$` 字面量）。

## 9. Bug 与修复历史（为什么现在是这么设计的）

> 这一章不是考古。**每条规则下面都有一个真实事故**，改代码前请先读。

### 9.1 事故一：草稿箱里只有标题，没有正文

**现象**：浏览器 CDP 发布"成功"，后台草稿箱里标题正确，**正文一片空白**。

**根因**（三层，逐层挖出来的）：

1. 编辑器里有**两个** `.ProseMirror`：外层是标题，正文是 `.rich_media_content .ProseMirror`。
   粘贴时聚焦错元素 → 内容跑到标题或丢了。
2. Xvfb `:99` **没有窗口管理器** → `xdotool` 发送的按键不可靠。
3. CDP 的 `Input.insertText` 是纯文本直插，走不通富文本；真正可用的是
   `Input.dispatchKeyEvent {key:'v', modifiers:2, commands:['paste']}`（等价 Ctrl+V）。
4. 即使聚焦对了，**粘贴前的一次 `file://` 临时标签页切换会把焦点重置**，
   于是 CDP 粘贴被静默丢弃。

**修复（三道防线）**

| # | 防线 | 位置 |
|---|---|---|
| 1 | 补丁：正文选择器 + **粘贴前重新聚焦并置光标到末尾** | `deploy/patch-baoyu-skill.sh`（v1+v2） |
| 2 | 上游技能自带修复（`prepareEditorPasteTarget()`：激活标签页、校验 `activeElement`、发现标题/作者抢焦点就修正或抛错） | baoyu-post-to-wechat v1.118.2 |
| 3 | **不管上游说成功没成功，都回后台读真实 DOM 校验正文** | `verifyDraftBody()` in `src/wechat.ts` |

> **第 3 条是唯一不可移除的**。前两条都是"让它别出错"，第三条是"出错能被发现"。
> 铁律：**信正文，不信标题；信后台，不信技能自报。**

### 9.2 修复：技能升级到 v1.118.2，补丁改为"自适应"

上游 v1.118.2 独立修复了同一个 bug（`BODY_EDITOR_SELECTOR = '.rich_media_content .ProseMirror'`，
新增 `prepareEditorPasteTarget()`），比本地补丁更严谨。处理方式：

- **先在 `/tmp` 试跑**再动线上（把上游 rsync 到 `/tmp/upstream-wps`，`bun install`，发一篇测试草稿，
  用探针量 `text/h2/p/strong/ul/li/blockquote` 数量）→ 实测文本 2298 字、`h2×6 p×32 strong×34 ul×7 li×25 blockquote×5`，与旧版一致。
- 备份可回滚：`/root/baoyu-post-to-wechat.v1.56.1.tgz`（17M）
- `clawhub --workdir /root/.agents update baoyu-post-to-wechat --force` → 1.118.2，再 `bun install`
- **升级会覆盖 `wechat-article.ts`，所以补丁脚本必须是自适应的**：
  检测到上游已有 `prepareEditorPasteTarget` → 打印"上游已原生修复，无需补丁"并退出 0；否则才打 v1+v2 补丁。
- **`doctor` 从"补丁在不在"升级为"能力在不在"**：正文选择器正确 **且**（有 `prepareEditorPasteTarget` **或** 有 `wechat-flow-patch v2`）才算 ✅。

> 教训：**别把"我打过补丁"当验收条件，要把"能力存在"当验收条件。**

### 9.3 事故二：rsync 一条命令清空了整个应用目录

**现象**：部署后 250 上的应用根目录被清空。

**根因**：`rsync -a --delete src1 src2 src3 dest/` ——
**多个源 + `--delete` + 目标以 `/` 结尾**时，rsync 按"把多个源的内容平铺进目标"处理，
配合 `--delete` 就删掉了目标里其它文件。

**修复**：`deploy/deploy.sh` **只允许单一源 + 结尾斜杠**，并把易误删的运行时目录全部排除：

```
config.json  data/  plans/  articles/  state/  imgs/  sessions/  logs/  .env
```

> 教训：**rsync 的源参数永远只写一个**；把不变式写进脚本，别靠记性。

### 9.4 修复：`${dry:+-n}` 让每次部署都变成 dry-run

`${dry:+-n}`：只要 `dry` **非空**就展开成 `-n`。而 `dry=0` 也是非空字符串 → **永远带 `-n`**，
部署从来没真的写过。

**修复**：改成显式的 `DRY_ARG=()` / `DRY_ARG=(-n)`。

> 教训：bash 的 `${var:+...}` 判断的是"空/非空"，不是"真假"。

### 9.5 修复：部署守卫误报（把"本地改了"当成"冲突"）

第一版守卫用 `rsync -ain --checksum --delete` 比对本地与 250 的 `content/`、`prompts/`，
**只要不一致就中止**。问题：正常推送（本地改了要发上去）本来就不一致 → **每次部署都被拦**。
另外还误把 `.f..t......`（仅 mtime 不同、内容相同）当成差异。

**修复（两步）**

1. 只看真实增删改：过滤 `grep -E '^[<>ch*]'`，行首 `.` 的"无更新"行不算（`.f..t` 不再误报）。
2. **改用"上次部署指纹清单"判定**：部署成功后把 250 上 `content/`+`prompts/` 的 `sha1sum` 清单
   写到 `data/_content-backup/deployed.sha1`。下次部署时对比当前指纹与清单：
   - 相同 → "250 上未被修改，可以安全覆盖"（正常推送）
   - 不同 → 才是"**250 上有人改过**" → 中止并给三个选项

```bash
./deploy/deploy.sh                       # 常规：250 未被改则直接部署
./deploy/deploy.sh --force-content       # 覆盖 250（先自动备份到 data/_content-backup/<时间戳>/）
./deploy/deploy.sh --keep-remote-content # content/ prompts/ 不同步，250 为真源
./deploy/deploy.sh -n                    # 只预演
```

实测（模拟 250 被改）：

```
⚠️  250 上的 content/ 或 prompts/ 在上次部署之后被改过了：
      < 1fdca0ea…  content/syllabus.md        ← 上次部署时的版本
      < 65a84173…  prompts/editor.md
      > 437f21af…  prompts/editor.md          ← 250 上的当前版本
当前策略：**本地仓库为真源**。请选一个：
  1) 想保留 250 上的改动 → 先把它们同步回本地仓库，再重新部署
  2) 以后就想在 250 上改 → ./deploy/deploy.sh --keep-remote-content
  3) 确认要丢弃 250 的改动 → ./deploy/deploy.sh --force-content
```

### 9.6 修复：`deploy.sh` 的守卫自己把自己打死了

`set -euo pipefail` 下，`diff a b | grep … | head` 里 `diff` 因"有差异"返回 1，
被 **`pipefail`** 视为管道失败 → **脚本在打印提示前就退出**，用户只看到 diff 不给选项。

**修复**：该管道末尾加 `|| true`。

> 教训：`set -e` + `pipefail` 下，任何"用非零退出码表达正常结果"的命令（`diff`、`grep`）都要 `|| true`。

### 9.7 修复：`plan --dry-run` 会误覆盖本周计划

`plan` 的产物是 **pi agent 自己写文件**的（提示词里给了 `{{planPath}}`），
所以 `--dry-run` 只是"不记录"，文件其实已经被写掉了 —— 手改过的本周计划会被覆盖。

**修复**：`--dry-run` 时让 agent 写到旁路文件 `<周>.dryrun.json`，校验通过后删掉，**不碰真实计划**。

> 教训：**当"写文件"的是 AI 时，`--dry-run` 必须在路径层面隔离**，不能只在代码里"不记录"。

### 9.8 修复：公式文章被安全网误判成"空正文"

公式渲染成 SVG 后**不含任何文字**。一篇公式多的文章纯文字数偏少，被
`verifyDraftBody(minChars=200)` 拦下（实测：文字 161 字 + 4 公式 + 1 动图 → 误判失败）。

**修复**：判据改为**加权内容量** —— `文本 ≥ 60` 且 `文本 + 80×svg + 80×img ≥ 200`，
日志里同时打印 `svg`/`img` 数量和折算值。

```
[INFO] draft body verified: body=161 chars, svg=4, img=2, 折算内容量=641 (min 200)
```

> 教训：新增内容形态（SVG/GIF）后，**校验指标必须同步升级**，否则安全网会变成拦路虎。

### 9.9 其他已确认结论（避免重复踩坑）

| 结论 | 说明 |
|---|---|
| 浏览器路径才支持 GIF | `wechat-image-processor.ts`（API 路径）拒绝 gif 且限 1MB |
| 微信会重设图片宽度 | GIF 上传后是 `data-w=640`，实际显示宽度由微信决定，你只要保证清晰 |
| 删除草稿 | `POST /cgi-bin/operate_appmsg?...sub=del&type=77&appmsgid=<id>&isMul=0` |
| 草稿列表 | `GET /cgi-bin/appmsg?...action=list_ex&type=77&count=20` |
| 编辑器 token | 从首页 URL 取：`new URLSearchParams(location.search).get("token")`（正则取法会失效） |
| 空正文占位符 | `从这里开始写正文`（10 字），测量前必须剔除 |
| `--all` 与 `cdpPort` | 每个账号必须独立端口，否则两个号互相踩踏 |
| 上游模型不稳定 | `justwoker/claude-opus-4-8` 会 503；已配 `model.article.fallbacks` 自动降级 |
| 微信 API 白名单 | `errcode 40164 invalid ip`（API 发布路径被卡，所以选了浏览器方案） |

## 11. 故障排查速查

| 症状 | 先看 | 处理 |
|---|---|---|
| 到点了没发 | `systemctl list-timers 'wechat-*' --all` | timer 被停了 → `systemctl enable --now wechat-publish.timer` |
| 发了但草稿箱空正文 | `journalctl -u wechat-publish.service -n 200` | 看 `draft body` 那行；若 `svg/img` 都有但文本 0 说明公式加权生效中；真为空则 `doctor` 看"正文写入能力" |
| `no enabled accounts` | `bun src/cli.ts accounts` | 所有号的 `enabled` 都是 false，打开一个 |
| `no plan for <date>` | `ls data/<alias>/plans/` | 计划没生成 → `bun src/cli.ts plan -a <alias>` |
| `draft not found in 草稿箱` | `bun src/cli.ts drafts -a <alias>` | 技能没真的写进去 → 跑 `doctor`，看登录态与技能 |
| 登录失效 | `bun src/cli.ts doctor -a <alias>` | `bun src/cli.ts login -a <alias> --qr`（二维码可发邮件） |
| 模型 503 / 402 | `journalctl ...` 看 `pi` 输出 | 改 `config.json` 里 `model.article.fallbacks` 换可用模型 |
| 邮件没到 | `bun src/cli.ts mail-test -a <alias>` | 看 `/root/.claude/skills/email-sender/` 配置与授权码 |
| 公式没渲染 | `doctor` 的 `latex 公式` 行；日志 `公式未渲染` | 检查公式里有没有中文；`rm -rf data/<alias>/imgs/formula` 清缓存 |
| GIF 不动 | `bun tools/draft-probe.ts <端口> open` 看 img src | 必须是 `mmbiz_gif`；不是则上传的是 png |
| 两个号互相覆盖 | 自查 `config.json` 的 `cdpPort` | 必须唯一（9222/9223/…） |
| 部署被拦 | 部署输出的 `被改过了` | 按提示三选一（见 [9.5](#95-修复部署守卫误报把本地改了当成冲突)） |

**看实时日志**


### 12.4 术语表

| 词 | 意思 |
|---|---|
| **计划 / plan** | `data/<alias>/plans/<ISO周>.json`，一周 7 天的选题 |
| **草稿箱** | 公众号后台的草稿，需人工点"群发"才真正发出 |
| **CDP** | Chrome DevTools Protocol；本项目用它在浏览器里"手动"操作公众号编辑器 |
| **内联 SVG** | 直接嵌在 HTML 里的矢量图，本项目用它承载 LaTeX 公式 |
| **场景 / scene.py** | manim 动画脚本，固定放在 `imgs/<日期>/`，类名固定 `Scene` |
| **指纹清单** | `data/_content-backup/deployed.sha1`，记录上次部署时 250 上的内容哈希 |
| **安全网** | `verifyDraftBody()`，发布后回后台读真实 DOM 校验正文 |
