# Cross-Environment Handoff（跨环境 / 跨 Agent 交接）

> **定位**：本约定解决的是「**换环境之后**怎么把活接下去」，与 `AGENT.md` 解决「**同仓同环境**怎么续接」互补。
> **核心原则**：交接稿是 `AGENT.md` 的**投影（projection），不是替代（replacement）**。
> 状态真相源永远是 `.trellis/`（tasks / spec / workspace）+ `AGENT.md`；交接稿只负责**把真相源翻译成对方环境可执行的开工指令**。

---

## 1. 何时必须写交接稿（触发条件）

命中任一即写；全不命中则不要写（避免产生无人维护的文档）：

| 触发条件 | 例子 |
|---|---|
| **换 Agent / 换平台** | 本地 pi ↔ CNB Agent、Cursor ↔ Codex、跨厂商 Agent 接力 |
| **换机器 / 换环境** | 本地开发机 → 目标机 250；本地 → 云开发容器（环境差异会决定对方能否跑通验证命令） |
| **跨会话长任务分段** | 一次里程碑做不完，需要对方从「当前 Checkpoint」继续 |
| **需要对方独立开工** | 对方看不到你的上下文、也读不到你的聊天记录，必须自带全部前提 |
| **交付边界需要留痕** | 对外/对他人交付一段工作，事后要能复盘「当时交接了什么、按哪版执行」 |

**不需要写**：同一会话内的继续、同一 Agent 换话题、纯问答。

---

## 2. 必含章节清单（缺一不可）

顺序即为**对方的执行顺序**。每一节都必须落到可验证的路径或命令，禁止只写意图。

| # | 章节 | 必须回答的问题 | 落地要求 |
|---|------|----------------|----------|
| H1 | **仓库与环境基线** | 仓库 URL、分支、**基线 commit SHA**、远端个数与名称？技术栈与版本（如 bun ≥1.3）？ | SHA 必须写全或写短前 7 位；"两侧已同步"必须注明 SHA |
| H2 | **哪些东西不在仓库里** | 被 `.gitignore` 的配置/密钥/运行时数据有哪些？对方从哪拿？ | 逐条列路径（如 `config.json` / `.env` / `data/`），并写明"**向我索取，不许猜**" |
| H3 | **续接读取顺序 + 读取上限** | 先读哪 1–3 个文件？哪些禁止整读？ | 显式给出文件名与顺序；给出读取上限（本项目：单次 ≤3 个非 `AGENT.md` 文件） |
| H4 | **铁律与硬约束** | 什么东西**未经确认绝不能动**？零依赖/隔离/真相源等红线？ | 引用 `.trellis/spec/` 与 `AGENT.md` 的章节号，不要复述全文 |
| H5 | **工作流与门（GATE）** | 任务怎么起、什么时候必须停下来等人？真机验收门？ | 写清 task 生命周期命令与"批准前不写代码"这类硬停点 |
| H6 | **待办与依赖顺序** | 做哪些任务、什么顺序、谁依赖谁、验收标准编号？ | 直接指向 `.trellis/tasks/<task>/{prd,implement}.md` 与 AC 编号，禁止在交接稿里重写需求 |
| H7 | **已知偏差 / 坑** | 真相源与现状不一致之处（避免对方误判为"没这些任务"）？环境特有的坑？ | 例如"`AGENT.md` 看板尚未含 S11 阶段，这是已知缺口，由 P8 修复" |
| H8 | **汇报格式与证据规则** | 对方交付时按什么格式回报？"完成"如何界定？ | 固定格式：一句话结论 + 产物路径/命令输出摘要 + 待确认点 |
| H9 | **Git 约定** | 分支、提交信息风格、推哪些远端、推完回报什么？ | 明确禁止提交密钥/配置/运行时数据 |
| H10 | **现在开始做什么** | 第一件具体动作是什么？ | 必须是**单一可执行动作** + 明确的等待点（"先做 X，然后给我 Y，等我批准") |

> 可直接复制的骨架见 [`docs/handoffs/TEMPLATE.md`](../../../docs/handoffs/TEMPLATE.md)；
> 归档与命名见 [`docs/handoffs/README.md`](../../../docs/handoffs/README.md)。

## 3. 证据与密钥边界（硬约束）

### 3.1 禁止写入交接稿的内容

**任何情况下都不得**把下列内容写进交接稿、提交、或粘贴到会留痕的位置：

| 禁止项 | 为什么 | 正确做法 |
|---|---|---|
| 明文 token / PAT / API key | 交接稿常被整段复制到聊天记录、工单、其他人可见的 Agent 会话 | 只写"需要 XX 平台的 token，请到 XX 控制台签发" |
| 把 token 嵌进 git remote URL（`https://user:token@host/...`） | 会明文落进 `.git/config`，且 `git remote -v` 直接打印 | 用凭据存储（`credential.helper=store` + `~/.git-credentials`，权限 600），URL 保持干净 |
| master key / 加密盐 / DB 口令 | 一旦泄露等于凭据全泄露 | 写"由环境变量注入，值请我在部署时提供" |
| `config.json` / `.env` 的真实内容 | 含邮箱口令、后台账密、cookie 路径等 | 只写字段名与来源，例：`mailer.*`，值从 `config.example.json` 复制后本地填 |
| `data/` 下的运行时状态（session / state / audit） | 属运行数据，非真源；提交会污染仓库 | 让对方**重新生成**，不要搬运 |

> **已发生的教训（2026-10-13）**：曾把 cnb 访问令牌直接写进 `remote.cnb` 的 URL，
> 令牌随之出现在 `.git/config` 与 `git remote -v` 输出中，只能吊销重签。**交接稿出现 token 一律视为事故。**

### 3.2 证据规则（与 `AGENT.md` §6 一致，不得放宽）

- 「完成」= **产物真实路径存在** 或 **命令真实输出**；不接受"应该没问题""我记得做过了"。
- 交接稿里给出的每条验证命令，必须是**对方环境里真能跑**的命令；不能跑就写清前置条件（缺 bun、缺 Chrome、缺 250 机器访问）。
- 交接稿中引用的**每个路径都必须真实存在**（写完后用 `test -e` 逐条验一遍）。

## 4. 口径原则：投影，不是替代

1. **不另起事实**：进度、任务清单、GATE 状态一律从 `AGENT.md` + `.trellis/tasks/` 派生；交接稿中如与真相源冲突，**以真相源为准**，并立刻修正交接稿。
2. **引用而非复述**：写"见 `AGENT.md` §2 GATE / `.trellis/spec/engine/index.md`"，而不是把内容抄一遍——抄一遍就会产生第二个需要同步的版本。
3. **显式声明偏差**：真相源暂时不完整时（例如看板还没登记新阶段），必须在交接稿 H7 明确写"这是已知缺口、由哪一步修复"，否则对方会认为需求不存在。
4. **需求有分歧 → 改 `prd.md`**，不要只在交接稿里写。

## 5. 生命周期（防止过期交接稿被当现役指令执行）

```
生成 → 归档（docs/handoffs/YYYY-MM-DD-<用途>.md）→ 执行中（有效）→ 交付/归档 → 标记失效
```

- **头部必写三件事**：生成时间、基线 commit SHA、失效条件。
  失效条件示例：「全部子任务验收通过并归档」「被更新的交接稿取代」「基线 commit 落后超过 N 个提交」。
- **失效标记**：任务归档或交接目标达成后，在该文件头部补一行 `> **状态：已失效（YYYY-MM-DD）** —— 原因：…`；
  **不要删除**，交接历史本身是复盘材料。
- **执行前自检**：接手方开工前先比对交接稿的基线 SHA 与当前 `HEAD`；不一致就先 `git log --oneline <sha>..HEAD` 看差异，判断交接稿是否仍适用。
- **一稿一目标**：一份交接稿只服务一个明确目标（如"完成控制台 C1–C6"）；目标变化就写新稿，不要续写旧稿。

## 6. 反模式（写交接稿时禁止）

| 反模式 | 后果 |
|---|---|
| 把整篇 `README.md` / 操作手册内容抄进交接稿 | 交接稿膨胀成第二个真相源，必然与仓库漂移 |
| 只写"继续之前的开发"而不给基线 SHA 与任务路径 | 对方无从判断现状，只能重新调研甚至重做 |
| 隐含假设对方有你的环境（有 bun/Chrome/250 访问权、有 config.json） | 对方第一条命令就失败，来回确认成本高于写清前置条件 |
| 把 GATE 写成"注意一下"而不是硬停点 | 对方直接改动发布链路，绕过真机验收 |
| 交接稿里出现 token / 明文口令 | 安全事故（见 §3.1） |
| 交接完成后不标记失效 | 下一个人拿旧稿开工，做出已经变过的需求 |

---

## 7. 维护

- 本约定本身的修改：改本文件 + 同步 `docs/handoffs/TEMPLATE.md` 的章节（两者**必须同构**，改一处就改另一处）。
- 新发现的高价值交接经验（新的环境坑、新的必含章节）→ 追加到 §2 / §6，并在 `AGENT.md` §9 变更日志登记。
